# 质量与审查规范

## 通用内容权威与三本账

将以下记录严格分开，不得互相冒充：

1. `content-advice.json`：Agent 对事实、措辞、结构、叙事、审美、专业性或内容风险的参考建议。所有条目的 `gate_effect` 必须为 `NONE`；无论优先级、用户是否回复或是否采纳，都不得影响项目状态、提交授权、项目经理验收或下游推进。用户拒绝后记录 `REJECTED` 并结束，不得重新争论。
2. `review-items.json`：用户提出、尚待执行或回答的要求。只有 `OPEN` 用户事项会阻止授权；处理完成后记录 `CLOSED`。Agent 自己提出的建议不得写入这里。
3. `stage-issues.json`：能够依据用户已批准的输入、配置、许可要求和技术契约客观复现的执行问题。只允许脚本列明的客观类别，不得登记内容正确性、措辞、审美、专业性或 Agent 风险判断。

用户最新明确内容决定写入 `owner-decisions.json`，状态为 `BINDING`。该决定对阶段 Session、项目经理、对抗审查、返工工单和下游阶段都有约束力。项目经理只检查决定是否被准确执行，不重新评价决定本身。

## 客观问题等级与阶段推进

- `BLOCKER`（阻断）：必需输入缺失、媒体或输出不可用、文件完整性损坏，或用户明确要求的权利证据缺失。
- `HIGH`（高）：可复现的重大同步、时间轴、布局、声音、渲染或配置符合性故障。
- `MEDIUM`（中）：不阻止交付但会降低用户既定技术目标的局部执行问题。
- `LOW`（低）：不影响正确交付的执行细节。

只有 `stage-issues.json` 中 `OPEN + BLOCKING` 的客观问题和 `review-items.json` 中 `OPEN` 的用户要求可以阻止推进。每个客观问题都要记录证据、负责人、修复动作、复测和关闭结果。不得因 Agent 内容建议未被采纳而退回阶段。

## 审查角色

必须取得以下角色的证据：事实挑战者、恶意误读者、普通观众、手机端与安全区审查者、动效执行者、剪辑与合成审查者、无障碍与字幕审查者、声音审查者、权利与许可审查者、可复现性审查者。内容类角色只能生成 `content-advice.json` 参考建议；技术执行角色只有在能够依据用户契约客观复现时才能生成 `stage-issues.json`。只有明确写出已检查证据后，角色才能报告“未发现问题”。

## 用户审批记录

把 Agent 参考建议、用户决定、用户要求和提交授权分开。审阅记录可以包含 `COMMENT`、`QUESTION`、`CHANGE_REQUEST`、`APPROVED`、`APPROVED_WITH_CONDITIONS` 或 `REVISION_REQUIRED`，用于保存用户批注、问答、内容决定和附加要求；这些状态一律不能授权提交。记录展示给用户的准确产物和版本、用户原话或忠实摘要、条件、处理状态、时间和记录人。用户沉默不等于批准，但 Agent 建议未获回复也不得阻断项目。审批静态审阅图不等于审批尚未展示的动画或混音。

P05 必须以 A 编号为单位逐场景审阅。每次展示对应独立动效脚本摘要和入场建立后、信息最完整时、交接前三张审阅图；只批准一张图、只批准设计系统或只批准部分场景，都不等于该场景包或 P05 全阶段完成。场景修改后更新脚本版本和三图中所有受影响图片，再重新取得该场景批准。P05 最终门禁要求场景包索引中全部场景为 `APPROVED` 且各有审批引用。

P00、P04、P05、P07、P08、P10、P14 采用双层门禁：阶段 Session 先完成全部审阅互动、修改、自检和最终版本冻结，再单独询问用户是否授权提交；只有用户明确表示“可以提交项目经理”后才能记录 `SUBMISSION_AUTHORIZED`。项目经理随后读取记录执行正式验收。两层缺一不可，项目经理不得补写、推断或代替用户授权。

请求最终提交授权前必须向用户汇总：最终产物及版本、用户决定的执行结果、用户附加要求状态、问答状态、开放客观阻断数量和提交范围。只有用户要求已关闭、问答已完成、开放客观阻断为零时才能请求授权。未采纳或未回复的 Agent 内容建议不计入未决事项。`APPROVED_WITH_CONDITIONS` 不能提交。

提交授权必须记录最终产物、版本、范围、用户明确授权原话、未完成用户要求为零、开放客观阻断为零、条件状态为 `CLOSED`、问答状态为 `COMPLETE` 和记录时间。授权后发生用户新要求、客观问题或产物变化，原授权立即失效；单纯新增 Agent 内容建议不改变项目状态，也不使授权失效。

## 视觉检查

- 每个场景只有一个认知结论和一条主要视觉路径；适当时至少设置两个视觉锚点。
- 屏幕文字、单位、限定条件和符号必须与用户最终锁定内容完全一致；Agent 参考建议不得擅自进入画面。
- 人物全程可见，人脸裁切稳定，V1、V2、V3 转换不得造成源时间跳变。
- 字幕区和动画区不得遮挡人脸或平台操作控件。
- 检查关键帧、转场边界、首尾帧、长文案压力场景及全部用户安全区边界。
- P05 每个 A 场景恰好提供三张真实内容审阅图；P09 同角色实现帧必须逐一对照，不得用联系表缩略图或通用线框代替。
- HyperFrames 的 `lint` 和 `validate` 必须通过；`inspect` 不得有无法解释的溢出；对比度警告必须解决；动画异常标志必须修复或给出合理说明。

## 声音与同步检查

- 标准 MP3 从主时间轴零点开始，不得发生未经审批的偏移、拉伸或替换。
- 口播清晰且无削波；背景音乐按规则自动压低；音效不得掩盖语音。
- 比较总时长、开头、多个内部语音地标和结尾。把漂移视为源文件或时间轴问题，不得用随意调整场景偏移来掩盖。

## 字幕检查

- 文本和时间码已经校正；同一时刻只有一组字幕；字幕不得重叠；每组结束后必须确定性强制隐藏。
- 默认整句模式。拆分时必须保持语义从句、否定词、数字与单位、名称和限定条件完整。
- 开启字幕时默认交付带字幕成片及 SRT、VTT。只有用户要求时才制作无字幕成片。

## 技术检查

使用 FFprobe 检查每个最终文件。验证时长、分辨率、显示宽高比、帧率、封装格式、视频与音频编码、音频采样率和声道、起始时间及可解码性。抽样检查黑帧、冻帧和损坏帧；必须检查真实交付文件，而不是预览代理文件。为每个交付文件生成哈希。

## 完成定义

P14 已验收；全部请求的成片版本都存在；可编辑源工程和确定性命令已包含；输入、配置、用户决定、审批和版本沿革已保存；不存在开放的客观阻断问题或未完成用户要求；权利状况和用户要求记录的限制已披露。Agent 内容建议是否采纳不影响完成定义。
